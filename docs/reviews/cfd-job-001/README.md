# cfd-job-001 — the controller plans, the host executes, the controller assesses

**Bundle id:** `cfd-job-001`
**Type:** execution layer (no agent episode; no LLM behaviour in this bundle)
**Status:** EvoCFD's own controller code planned a real OpenFOAM solver run,
the host executed it, and the controller assessed the outcome from the solver's
log. The job reached its requested physical time and used the real-fluid
property path.

---

## Question

Can the controller plan a real solver run, have it executed somewhere the
controller itself cannot run, and assess what happened from evidence rather
than from anyone's assertion?

This is the execution layer the reviewer asked for as a primitive distinct
from `runEpisode()`, and it is the bridge between `realfluid-baseline-001`
(which proved the solver exists) and CFD-001 (which will put a fault in front
of an agent).

## The boundary, and why it is three phases

The controller is a Node toolchain in the campaign container. The solver was
built on the host against system gcc and system Open MPI, and its binaries link
`libmpi.so.40`, which the container does not provide. Mounting the host
binaries into the container does not make them runnable:

```text
reactingFoam: error while loading shared libraries:
  libmpi.so.40: cannot open shared object file: No such file or directory
```

The mount succeeded, the binary was visible and executable, and it still could
not run. That is exactly the reviewer's point: *mounting host-built binaries
into a container is not, by itself, a demonstration that the runtime
dependencies are compatible.*

Rebuilding the solver inside a container would be a second, differently-
identified build — a new environment to record, not a fix for this one. So the
boundary is made explicit instead:

| Phase | Where | What |
|---|---|---|
| `plan` | campaign container | writes the write-once job record and a runner script with the exact planned command |
| `run` | host | executes the runner, where the solver's libraries are |
| `assess` | campaign container | derives the terminal state from the solver's log alone |

The runner script is generated by the `plan` phase, so the command the host
executes is the command the record describes — the host cannot improvise. And
the `assess` phase does not take the host's word: it reads the log and decides.
A run and its assessment therefore cannot disagree about the outcome.

## Observed

```text
job 1D-advection-001: finished
  solver log ends with a normal End
  requested endTime 0.002, reached 0.002
ok the job reached its requested physical time through the controller
```

The job record, in `records/job-record.json`, is self-authenticating: the plan
digest recomputed at read time matches the one written at submission, so a
re-planned job is detectable rather than silent.

The solver's own log shows the real-fluid property path was selected:

```text
mixture         PRchungKineticMixture;
transport       chungKinetic;
thermo          rfJanaf;
equationOfState PengRobinson;
specie          rfSpecie;
```

## Evidence

- `records/job-record.json` — the plan, the derived state, and the plan digest,
  exactly as the controller wrote and read them back.
- `records/execution.json` — machine-readable phase split, outcome and the
  boundary between supported and unsupported claims.
- `logs/cfd-job-excerpt.txt` — the runner script, the log head, the
  thermophysical selection, the log tail, the sampled times, and the full job
  record.

## Trust

- The agent never receives the docker socket and never invokes the solver. Both
  are controller capabilities; the plan is recorded before anything runs.
- The job record is written with an exclusive open, so a second plan for the
  same job is an error rather than an overwrite. The state advances, the plan
  and its digest do not.
- `assess` derives state from the log: a normal `End` is `finished`, time
  steps without a normal end is `failed`, and no output at all is a failed
  execution with the reason recorded. There is no path from "the host said it
  went fine" to a `finished` state.

## Limitations

- **One serial, non-reacting case.** Nothing about MPI decomposition, about
  combustion, or about numerical accuracy. This proves the execution layer
  works against a real solver, nothing more.
- **The container cannot run this build.** The controller and the solver are in
  different trust domains with different toolchains. A trial that claims to
  have used the `of8-realfluid` profile must record *where* the solver ran,
  because a host-side and a container-side execution of the same digest are
  different claims.
- **Process facts, not numerical judgement.** The assess phase reports whether
  the solver ran, reached the requested time, and ended normally. Whether the
  result is *good* is a separate assessment, not implemented here.
- **No reproducibility claim.** The digests identify artefacts; they do not
  prove a rebuild is bit-for-bit identical.

## Review requested

1. The runner script is generated by the `plan` phase and the host executes it
   verbatim. Is that sufficient binding between the recorded plan and what ran,
   or should the runner also record its own execution evidence — start time,
   exit code, and a digest of what it produced — so the assess phase has more
   than the solver's log to reason about?
2. The container cannot run the solver. Should EvoCFD record the *execution
   domain* (host or container) as part of trial identity, so that a host-side
   run and a container-side run of the same plan are not conflated?
3. The assess phase currently distinguishes three outcomes from a log. Is that
   the right granularity for a job whose solver diverges — reaching many time
   steps and then ending abnormally is currently `failed`, but a reviewer may
   want divergence reported separately from a crash.

## What this unblocks

The execution layer exists and is proven against a real solver. CFD-001 can now
be built on it: a controlled provenance mismatch, injected only in a disposable
fixture workspace, where the correct setup is known to be runnable and the
injected difference is the only difference between passing and failing.
